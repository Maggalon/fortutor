# Подключение интеграций

Значения ниже задаются в `.env.local` для разработки и `.env.production` на VPS. Web и worker используют одни и те же PostgreSQL, Redis, S3 и bot/API keys. После изменения ключей пересоздавайте оба контейнера с `--force-recreate`: обычный `docker compose restart` не обновляет окружение. Не добавляйте секреты в `NEXT_PUBLIC_*`. Первый deployment возможен с пустыми ключами ЮKassa; подключение магазина, автоплатежей и чеков описано в [BILLING.md](BILLING.md).

## Окружение

| Переменная                                    | Назначение                                                                                                                             |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `DEMO_MODE`                                   | В production строго `false`                                                                                                            |
| `APP_URL`                                     | Канонический адрес без завершающего `/`, например `https://tutor.example.com`; используется в приглашениях, webhooks и проверке Origin |
| `DATABASE_URL`                                | PostgreSQL URI; пароль URL-encode, если есть специальные символы                                                                       |
| `DATABASE_SSL`                                | `true` для облачного PostgreSQL с доверенным TLS; `false` для внутренней Docker-сети                                                   |
| `REDIS_URL`                                   | `redis://...` или `rediss://...` с паролем и номером DB; постоянный Redis с поддержкой BullMQ/Lua                                      |
| `S3_ENDPOINT`                                 | Endpoint S3-провайдера; для AWS можно оставить пустым                                                                                  |
| `S3_REGION`, `S3_BUCKET`                      | Регион и приватный bucket                                                                                                              |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`    | Ключи доступа только к bucket приложения                                                                                               |
| `S3_FORCE_PATH_STYLE`                         | `true` для провайдеров, требующих path-style (например MinIO); иначе `false`                                                           |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` | Токен и username без `@`                                                                                                               |
| `TELEGRAM_WEBHOOK_SECRET`                     | Независимый случайный секрет, нужен в режиме `webhook`                                                                                 |
| `TELEGRAM_UPDATE_MODE`                        | `polling` по умолчанию: worker получает сообщения через исходящий транспорт. `webhook` требует доступности VPS из сети Telegram        |
| `TELEGRAM_PROXY_URL`                          | Необязательный HTTP/HTTPS-прокси только для Telegram: `http://USER:PASSWORD@HOST:PORT`; логин и пароль URL-кодируются                  |
| `MAX_BOT_TOKEN`, `MAX_BOT_URL`                | Токен официального API и публичная ссылка бота                                                                                         |
| `MAX_WEBHOOK_SECRET`                          | Другой случайный секрет webhook                                                                                                        |
| `MAX_API_URL`                                 | По умолчанию `https://platform-api2.max.ru`                                                                                            |
| `DEEPSEEK_API_KEY`                            | Ключ DeepSeek с доступным балансом                                                                                                     |
| `DEEPSEEK_MODEL`                              | По умолчанию `deepseek-flash`; доступная модель выбранного аккаунта                                                                    |
| `DEEPSEEK_API_URL`                            | По умолчанию `https://api.deepseek.com`                                                                                                |

В Linux секрет можно сгенерировать `openssl rand -hex 32`. Для Telegram используйте допустимые символы secret_token (hex подходит). Не используйте одинаковые секреты двух webhook-каналов.

## Telegram

1. Создайте бота через BotFather, получите token и username.
2. Заполните токен и username бота, при необходимости `TELEGRAM_PROXY_URL`. Откройте публичный `APP_URL` по HTTPS и проверьте `/api/health`. Для получения сообщений по умолчанию используется polling; секрет webhook нужен только при `TELEGRAM_UPDATE_MODE=webhook`.
3. Выполните `pnpm bots:setup` локально с `.env.local` либо команду настройки из инструкции VPS. Скрипт сверяет username через `getMe`, отключает webhook **без удаления ожидающих обновлений** и обновляет меню команд. Worker получает сообщения через `getUpdates` (long polling на 20 секунд) и тот же HTTP-прокси, что используется для ответов. Полученные события и следующий offset сохраняются атомарно в PostgreSQL; при перезапуске worker продолжает с сохраненного offset. PostgreSQL advisory lock исключает одновременный опрос одним токеном из разных worker. В режиме `webhook` скрипт вместо этого устанавливает `/api/webhooks/telegram` и secret_token. Username должен соответствовать токену; ведущий `@` и ссылка `https://t.me/…` нормализуются. [Способы получения обновлений Telegram](https://core.telegram.org/bots/api#getting-updates).
4. Ученик регистрируется по приглашению → «Настройки» → «Подключить Telegram» → «Открыть в приложении Telegram» или «Открыть через t.me» → Start. Ссылка одноразовая, действует 15 минут. Если переход не работает, в окне подключения показаны username и готовая команда `/start КОД`: найдите бота в приложении и отправьте ее вручную. Сайт остается открытым и обновляет состояние привязки. Родитель открывает бота и отправляет код из карточки ученика. Код одноразовый; после использования в карточке появляется новый.
5. `/start` и `/help` показывают меню; `/balance` работает у учеников и родителей. `/homework` или кнопка «Сдать ДЗ» запускает выбор предмета, задания, загрузку файла/фото, затем «Подтвердить отправку». До подтверждения работа не считается сданной. `/cancel` отменяет текущую отправку; `/unlink` отключает привязки этого пользователя в данном канале. Команды с `@username` и пробелами также принимаются. Команды и текст сообщения под нажатой кнопкой не добавляются к ответу ученика.

Проверка webhook через API `getWebhookInfo`: смотрите pending_update_count и last_error_message. Для просмотра не вставляйте токен в публичные сообщения или логи CI. [Официальная документация Telegram](https://core.telegram.org/bots/api#setwebhook).

### HTTP-прокси для Telegram

Если сервер не соединяется с `api.telegram.org:443` и получает `ETIMEDOUT`, задайте `TELEGRAM_PROXY_URL` в серверном `.env.production`. Формат, выдаваемый прокси-провайдером `HOST:PORT:USER:PASSWORD`, преобразуется в `http://USER:PASSWORD@HOST:PORT`. Зарезервированные символы в логине/пароле нужно URL-кодировать. Для подключения используется HTTP CONNECT с Basic-аутентификацией; TLS-сертификат Telegram проверяется как обычно.

```dotenv
TELEGRAM_PROXY_URL=http://USER:PASSWORD@HOST:PORT
```

Прокси используется для Telegram Bot API, получения сообщений через polling, настройки webhook, отправки ответов и скачивания Telegram-вложений. MAX, ЮKassa, DeepSeek и S3 сохраняют свой транспорт. В режиме `webhook` Telegram обращается напрямую к публичному HTTPS-домену через Nginx Proxy Manager: исходящий прокси этот маршрут не исправляет. Если `getWebhookInfo` показывает `Connection timed out`, а запросы к API работают, используйте `polling` (теперь это режим по умолчанию). Без `TELEGRAM_PROXY_URL` исходящие запросы к Telegram идут напрямую.

Файл `.env.telegram-proxy` сам по себе не загружается приложением и не попадает в Docker-образы. На VPS значение должно находиться в `.env.production`: этот файл используется web, worker и контейнером настройки. `bots:check` показывает, включен ли прокси именно в запущенном процессе; настройка при deployment также выводит `HTTP proxy enabled` либо `direct connection`. Открытие `t.me` на компьютере/телефоне использует сеть устройства, а не серверный прокси.

После первого deployment версии с поддержкой прокси добавьте строку в `.env.production`. Из каталога проекта на VPS выполните:

```sh
set -a
source .release
set +a
docker compose --env-file .env.production -f deploy/compose.production.yml up -d --no-deps --no-build --force-recreate web worker
docker compose --env-file .env.production -f deploy/compose.production.yml run --rm --no-deps worker node --import tsx scripts/setup-bots.ts
```

При последующем изменении прокси пересборка не нужна, достаточно пересоздать контейнеры. Учетные данные храните только в env-файле; не переносите их в Git, Dockerfile или workflow. Ошибки транспорта Telegram не выводят адрес прокси, его пароль или токен бота. [Undici ProxyAgent](https://github.com/nodejs/undici/blob/main/docs/docs/api/ProxyAgent.md).

## MAX

1. Зарегистрируйте бота по действующим правилам официального портала MAX, получите token и публичную ссылку. Возможность создания бота зависит от доступа вашего аккаунта на стороне MAX.
2. Заполните MAX-параметры. `MAX_BOT_URL` — публичная HTTPS-ссылка бота на `max.ru`; приложение задает параметр `start` для привязки ученика, сохраняя остальные query-параметры. В окне подключения также доступна готовая команда для ручной отправки.
3. Запустите `bots:setup`. Создается подписка на `bot_started`, `message_created`, `message_callback`, endpoint `/api/webhooks/max`; через `PATCH /me/commands` регистрируются те же команды, что в Telegram. Ошибка одного канала не мешает настроить другой. [Официальный метод команд MAX](https://dev.max.ru/docs-api/methods/PATCH/me/commands).
4. Ученик использует кнопку MAX в своем кабинете; родитель отправляет код. Диалог сдачи ДЗ такой же, как в Telegram. Входящие фото/файлы скачиваются с разрешенных HTTPS-доменов MAX и сохраняются в S3.

API получает токен в заголовке `Authorization`. Webhook проверяет `X-Max-Bot-Api-Secret`. Endpoint должен отвечать на HTTPS/443 с действующим сертификатом; событие сначала сохраняется в PostgreSQL, тяжелая обработка выполняется worker. [Подписки MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions), [отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages), [медиа](https://dev.max.ru/docs-api/use-cases/sending-messages/media).

## Проверка ботов на VPS

`deploy/update.sh` автоматически настраивает получение обновлений и команды после запуска новой версии web и worker. Telegram по умолчанию переключается на polling, MAX сохраняет webhook. Если `TELEGRAM_UPDATE_MODE` уже задан явно, этот выбор сохраняется. Если один канал недоступен, настройка второго все равно выполняется; deployment сообщает об ошибке настройки. Telegram-обновления при настройке не удаляются. Сам Telegram хранит неполученные обновления не более 24 часов.

Если список команд виден, а ответов нет, это не подтверждает работу webhook и worker. Запускайте диагностику **внутри работающего worker**, чтобы проверить его окружение и heartbeat:

```sh
set -a
source .release
set +a
docker compose --env-file .env.production -f deploy/compose.production.yml exec worker node --import tsx scripts/check-bots.ts
```

Скрипт показывает используемый транспорт (прокси/прямое соединение) и режим получения сообщений. Проверяет токены, соответствие Telegram username токену, команды и heartbeat worker. Для polling проверяет отсутствие webhook и последний успешный опрос в PostgreSQL; для webhook — адрес относительно `APP_URL` и подписки на сообщения/кнопки. Показывает число ожидающих обновлений Telegram, последнюю ошибку доставки и агрегированную очередь PostgreSQL. Значения секретов, содержимое сообщений и ID пользователей не выводятся. Старый `last_error_message` Telegram остается историческим: ориентируйтесь на дату ошибки и текущий `pending_update_count`.

- Username не соответствует токену: исправьте `TELEGRAM_BOT_USERNAME` и пересоздайте **web и worker** с `--force-recreate`.
- В режиме polling наличие webhook — ошибка: повторите настройку командой ниже. Если webhook отсутствует, но свежих опросов нет, проверьте логи worker, исходящий прокси и наличие других приложений, вызывающих `getUpdates` этим же токеном (Telegram вернет `409`).
- В режиме webhook он отсутствует или смотрит на другой домен: проверьте `APP_URL=https://for-tutor.ru`, затем повторите настройку командой ниже.
- Ошибка webhook `403`: секрет в работающем web отличается от использованного при настройке. Пересоздайте оба контейнера с одним `.env.production` и повторите настройку.
- Ошибка webhook `404`/`502` или TLS: проверьте публичный HTTPS-домен и маршрутизацию Nginx Proxy Manager до web. Рабочий HTTP health внутри контейнера не проверяет внешний webhook.
- Pending обновления растут, heartbeat отсутствует или есть ошибки доставки в очереди: проверьте `docker compose … logs --tail=100 worker` и исходящий доступ Telegram через настроенный прокси.

```sh
docker compose --env-file .env.production -f deploy/compose.production.yml run --rm --no-deps worker node --import tsx scripts/setup-bots.ts
```

Локальная диагностика API: `pnpm bots:check` с `.env.local`; проверка heartbeat требует запущенного локального worker.

## Сертификаты MAX API

MAX требует доверия к сертификатам Минцифры. В репозиторий включен `certs/max-ca.pem`: корневой и промежуточный сертификаты с официального сервиса Госуслуг. Dockerfile копирует bundle в оба готовых образа. `lib/max-transport.ts` добавляет эту цепочку к обычным CA только для запросов MAX API и его вложений; проверка имени сервера, сроков и подписи TLS остается включенной. Дополнительные env-параметры для этого не нужны.

Ошибка `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` после `Telegram webhook configured` относится к следующему запросу — настройке MAX. Выполните deployment версии с CA-bundle, загрузите текущие теги из `.release` и повторите `scripts/setup-bots.ts`. Установка сертификата только в ОС VPS не обновляет хранилище Node.js внутри уже работающего контейнера.

Публичные источники, отпечатки, сроки и команда обновления приведены в [certs/README.md](../certs/README.md). Перед окончанием срока промежуточного CA обновите bundle командой `node scripts/update-max-ca.mjs`, проверьте изменения и выполните deployment обоих образов. Bundle поставляется вместе с кодом, загрузка сертификатов во время запуска контейнера не требуется.

Если бот не отвечает: проверьте token, актуальный домен API, подписку, работоспособность worker, секреты и формат публичной ссылки. После долгой недоступности endpoint MAX может отключить подписку; повторите `bots:setup`. Если MAX меняет media CDN, добавляйте новый домен в `readMedia()` только после сверки с официальной документацией.

## DeepSeek

Для генерации отчета требуется API-ключ. Согласия собираются вне платформы; приложение не хранит и не проверяет флаг согласия. Передаются имя/предмет, период, посещаемость и проверенные задания с баллами/комментариями; платежные реквизиты, bot chat IDs и файлы не передаются.

«Отчеты» → «Сформировать отчет»: выберите ученика и период. Worker вызывает `/chat/completions`, сохраняет текст и ставит сообщения родителям в очередь. Статус «готов» означает, что текст сформирован; состояние доставки видно в задачах настроек. Без подключенного родителя отчет сохраняется в кабинете. Автоотчеты запускаются только для учеников с родительской привязкой: каждые 14 или 30 дней, начиная с создания профиля/последнего готового отчета.

При ошибке ключа, лимита или API задача повторяется до 5 раз; затем ее можно перезапустить в настройках. [Официальный Quick Start DeepSeek](https://api-docs.deepseek.com/quick_start). Название модели задается окружением, чтобы менять его без изменения кода.

## S3 и загрузка файлов

Создайте **приватный** bucket. Ключ приложения должен иметь `s3:PutObject`, `s3:GetObject` (включая HeadObject и CopyObject source); CopyObject требует PutObject на destination. Ограничьте доступ ARN этого bucket и его объектов. Public ACL не нужны. Для ботов S3 должен быть доступен из worker; для браузера — из сети пользователя.

Web загружает файл прямо в S3: `presign` → PUT временного объекта → `complete`. Сервер копирует его в отдельный окончательный объект, проверяет размер, Content-Type и сигнатуру. Продолжающая действовать ссылка PUT не может изменить уже приложенный файл. Не подтвержденные файлы нельзя прикладывать или скачивать. Подписанные ссылки действуют 5 минут; подтверждение допускается в течение 15 минут.

Установите bucket CORS (в консоли провайдера или AWS CLI; замените адрес своим):

```json
[
  {
    "AllowedOrigins": ["https://tutor.example.com", "http://localhost:3000"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 300
  }
]
```

Для AWS CLI оберните массив в `{"CORSRules": [...]}` и выполните `aws s3api put-bucket-cors --bucket YOUR_BUCKET --cors-configuration file://cors.json`. Не добавляйте wildcard origins для production. Настройте lifecycle: удаление объектов префикса `staging/` через 1 день. Окончательные объекты автоматически не удаляются: резервируйте их и задавайте срок хранения согласно своей политике. Неудачные/брошенные загрузки могут оставить неиспользуемые окончательные объекты; массовая очистка должна сверять ссылки PostgreSQL.

Лимиты: JPG/PNG/PDF, один файл до 20 МБ, максимум 10 файлов в одной работе. Проверка сигнатуры не заменяет антивирус: скачивание всегда идет как attachment. Бинарные web-файлы загружаются напрямую в S3, поэтому Nginx Proxy Manager пропускает только небольшие запросы API.
